Tier 1: Mental Model & Intuisi Fundamental WebSocket

Masalah Universal Komputasi: Mengapa WebSocket Diciptakan?

Protokol web tradisional (HTTP/1.1) didesain dengan model Request-Response yang sifatnya *half-duplex* dan *stateless*: client harus selalu bertanya terlebih dahulu agar server bisa menjawab.

Saat kita membutuhkan data *real-time* (misal: chat, update harga saham, atau koordinasi perangkat), cara naif di HTTP adalah Short Polling (bertanya berulang tiap detik). Polling menimbulkan pemborosan masif: setiap request HTTP membawa header berukuran ~800 byte (cookie, user-agent, headers) hanya untuk mendengar jawaban server: "Belum ada data baru".

WebSocket (RFC 6455) lahir untuk memecahkan masalah ini dengan membuka satu pipa koneksi TCP dua arah (full-duplex) yang persisten. Sekali koneksi tersambung, baik client maupun server bisa saling menembakkan data kapan saja tanpa perlu handshake berulang, dengan overhead frame biner yang sangat hemat (cuma 2–14 byte per pesan).

Analogi Universal: Telepon Langsung vs Kirim Surat Bolak-Balik

Bayangkan perbedaan mekanisme komunikasi berikut:

  • Model HTTP (Kirim Surat Pos): Setiap kali kamu butuh kabar, kamu harus menulis surat resmi lengkap dengan prangko dan alamat (HTTP Header), mengirimkannya via kurir, lalu menunggu surat balasan. Jika ingin tahu kabar tiap 2 detik, kamu harus terus mengirimkan surat baru.
  • Model WebSocket (Panggilan Telepon Langsung): Kamu menekan nomor sekali di awal (HTTP Handshake Upgrade). Begitu diangkat, gagang telepon tetap menempel di telinga. Siapa pun bisa berbicara atau mendengar secara instan tanpa perlu menutup dan menelepon ulang.

Jargon Buster: Kamus Istilah Esensial

  • Full-Duplex: Komunikasi dua arah simultan di mana kedua belah pihak dapat mengirim dan menerima data di waktu yang bersamaan tanpa saling menunggu.
  • Handshake Upgrade (HTTP 101): Transisi mulus di awal koneksi di mana client meminta izin ke server via HTTP biasa: "Boleh kita ubah koneksi ini jadi WebSocket?". Jika server setuju, status 101 Switching Protocols dikembalikan.
  • Half-Open Connection: Kondisi berbahaya di mana kabel fisik jaringan terputus mendadak, namun sistem operasi client atau server masih mengira koneksi dalam status ESTABLISHED karena belum menerima paket penutup (TCP FIN/RST).

Tier 2: Implementasi Teknis Fundamental (Minimal Working Code)

Sebelum masuk ke arsitektur KDS yang kompleks, perhatikan implementasi murni WebSocket di browser. Kode ini hanya terdiri dari ~15 baris yang menunjukkan siklus hidup native API tanpa library tambahan:

minimal-websocket-client.ts — Implementasi Dasar Tanpa Abstraksi 
// 1. Membuka koneksi TCP persisten ke server
const ws = new WebSocket("wss://echo.example.com");

// 2. Event saat handshake selesai & socket siap
ws.onopen = () => {
  console.log("Koneksi terbuka! Mengirim pesan perdana...");
  ws.send(JSON.stringify({ greeting: "Halo Server!" }));
};

// 3. Menerima frame data instan dari server
ws.onmessage = (event) => {
  const data = JSON.parse(event.data);
  console.log("Menerima data dari server:", data);
};

// 4. Menangani penutupan socket normal
ws.onclose = (event) => {
  console.warn(`Socket ditutup dengan kode: ${event.code}`);
};

① Inisialisasi & Transmisi Awal (Baris 1–8)

Input: URL WebSocket (protokol wss://).

Mekanika: Browser melakukan HTTP Handshake Upgrade. Begitu status berubah menjadi OPEN, event onopen terpanggil dan payload langsung dikirim tanpa header HTTP tambahan.

② Penerimaan Data Asinkron (Baris 10–14)

Mekanika: Kapan pun server memancarkan data, event onmessage langsung aktif. Tidak ada polling dan tidak ada request tambahan.

③ Lifecycle Penutupan Normal (Baris 16–19)

Mekanika: Dipicu saat server mengirim frame close (0x8) secara damai (*graceful disconnect*).

Tier 3: Abstraksi Kasus Spesifik — Kitchen Display System (KDS)

Sekarang mari kita bawa konsep dasar WebSocket ke arena nyata: Kitchen Display System (KDS) di restoran berkecepatan tinggi.

The Breaking Point: Mengapa Kode Dasar Tier 2 Meledak di Dapur?

  • Jebakan Half-Open Socket: Di dapur, tablet koki sering terhalang dinding stainless steel atau microwave. Sinyal Wi-Fi putus mendadak tanpa mengirim sinyal TCP FIN. Kode Tier 2 mengira socket masih hidup (OPEN), padahal tablet sudah tuli. Pesanan baru tidak pernah sampai dan koki tidak menyadarinya!
  • Serangan Badai Koneksi Ulang (Thundering Herd): Jika access point router dapur me-restart, 20 tablet KDS yang memakai kode Tier 2 akan reconnect secara serentak di milidetik yang sama, membuat backend WebSocket server langsung crash.
  • Packet Gap & Duplikasi Pesanan: Jika koneksi putus selama 10 detik, pesanan yang ditembakkan saat disconnect akan hilang selamanya karena kode Tier 2 tidak punya pelacakan urutan.

Invarian Domain Bisnis KDS

  • Zero Ticket Loss: Tidak boleh ada tiket pesanan yang hilang atau terlewat meski jaringan mati 5 menit.
  • Strict Monotonic Ordering: Pesanan steak Meja 4 harus dimasak sebelum makanan penutup Meja 4. Urutan tiket mutlak tidak boleh tertukar.
  • Station Isolation: Koki stasiun Panggangan (*Grill*) hanya boleh menerima pesanan daging, tidak boleh terdistraksi pesanan minuman atau salad.

Tier 4: Implementasi Teknis Kasus Spesifik (Potongan Modular Berurutan)

Alih-alih menumpuk 100 baris kode dalam satu file raksasa, kita bangun solusi KDS yang tangguh melalui 4 modul kecil independen (*bite-sized snippets*) yang masing-masing fokus menyelesaikan satu masalah spesifik:

Snippet 4.1: Heartbeat Watchdog & Deteksi Socket Mati Suri 
export class HeartbeatWatchdog {
  private pingIntervalTimer?: number;
  private pongTimeoutTimer?: number;

  constructor(
    private ws: WebSocket,
    private readonly intervalMs = 5000,
    private readonly timeoutMs = 3000
  ) {}

  public start(): void {
    this.pingIntervalTimer = window.setInterval(() => {
      if (this.ws.readyState === WebSocket.OPEN) {
        // Tembakkan probe PING manual di level aplikasi
        this.ws.send(JSON.stringify({ type: "PING", timestamp: Date.now() }));

        // Pasang batas waktu: jika 3 detik tidak ada PONG, socket dianggap mati suri
        this.pongTimeoutTimer = window.setTimeout(() => {
          console.warn("[KDS] Pong timeout! Socket mati suri. Memaksa close.");
          this.ws.close();
        }, this.timeoutMs);
      }
    }, this.intervalMs);
  }

  public handlePong(): void {
    // Reset timer saat balasan PONG diterima
    clearTimeout(this.pongTimeoutTimer);
  }
}

① Watchdog Aktif (Mencegah Half-Open)

Input: Instance WebSocket aktif.

Proses: Mengirim probe PING tiap 5 detik dan memasang alarm 3 detik. Jika Wi-Fi putus dan server tidak membalas PONG, socket langsung dipaksa close().

Output: Menghilangkan kondisi mati suri sehingga sistem langsung tahu kapan harus reconnect.

Snippet 4.2: Exponential Backoff dengan Full Jitter 
export function calculateJitteredBackoff(
  attempt: number,
  baseMs = 1000,
  maxMs = 15000
): number {
  // 1. Hitung penundaan eksponensial maksimal: 1s, 1.5s, 2.25s, ... hingga batas 15s
  const exponentialCap = Math.min(maxMs, baseMs * Math.pow(1.5, attempt));

  // 2. Terapkan Full Jitter: acak merata dari 0 hingga exponentialCap
  const delay = Math.random() * exponentialCap;
  
  return delay;
}

① Pencegah Thundering Herd

Input: Jumlah percobaan koneksi ulang (attempt).

Proses: Menghitung eksponensial lalu mengalikannya dengan faktor acak seragam.

Output: Menyebarkan gelombang koneksi 20 tablet KDS di waktu yang berbeda saat Wi-Fi kembali online, mencegah server tumbang.

Snippet 4.3: Pelacakan Urutan Monotonik & Deteksi Tiket Hilang 
export class MonotonicSequenceGuard {
  private lastSeq = 0;

  public processOrderEvent(
    event: { seq: number; ticket: any },
    onGapDetected: (missedSince: number) => void
  ): boolean {
    // 1. Abaikan event duplikat atau usang yang datang terlambat
    if (event.seq <= this.lastSeq) {
      console.warn(`[KDS] Event duplikat diabaikan: seq ${event.seq}`);
      return false;
    }

    // 2. Deteksi paket yang lompat (misal terima seq 105 padahal seq terakhir 103)
    if (event.seq > this.lastSeq + 1) {
      console.warn(`[KDS] Gap data terdeteksi! Meminta sinkronisasi ulang.`);
      onGapDetected(this.lastSeq);
    }

    this.lastSeq = event.seq;
    return true;
  }
}

Snippet 4.4: Server Gateway & Isolasi Channel Multi-Stasiun 
export class StationGatewayRouter {
  // Simpan client terkelompok per stasiun masak
  private stations = new Map>();

  public registerClient(stationId: string, ws: WebSocket): void {
    if (!this.stations.has(stationId)) {
      this.stations.set(stationId, new Set());
    }
    this.stations.get(stationId)!.add(ws);

    // Bersihkan referensi saat socket putus untuk mencegah Memory Leak
    ws.on("close", () => {
      this.stations.get(stationId)?.delete(ws);
    });
  }

  public broadcastToStation(stationId: string, payload: string): void {
    const clients = this.stations.get(stationId);
    if (!clients) return;

    for (const ws of clients) {
      if (ws.readyState === WebSocket.OPEN) {
        ws.send(payload);
      }
    }
  }
}

① Targeted Fanout & GC Safety

Input: ID stasiun dapur (GRILL, SALAD) dan payload pesanan.

Proses: Mengelompokkan socket ke dalam Set terisolasi dan langsung menghapusnya saat close agar V8 garbage collector bisa membebaskan memori.

Output: Hanya stasiun bersangkutan yang menerima data; hemat bandwidth Wi-Fi dapur hingga 80%.

Tier 5: Senior Engineering Trade-offs & Production Failure Modes

Edge Cases & Hidden Failure Modes

  • The "Ghost Cook Bump" (Jebakan Optimistic UI): Koki menekan tombol "Selesai" tepat saat koneksi Wi-Fi putus. Jika UI langsung menghapus tiket tanpa verifikasi ACK, tiket hilang dari layar koki tetapi di server masih berstatus pending. Solusi: Gunakan antrean offline IndexedDB dengan persistent replay saat koneksi pulih kembali.
  • Balapan Pembatalan Out-of-Order: Kasir membatalkan pesanan steak 1 detik setelah order dibuat. Jika paket pembatalan tiba lebih dulu karena perbedaan rute jaringan, buat tombstone record di state lokal agar tiket baru yang datang belakangan langsung di-drop.

Trade-offs Arsitektur: WebSocket vs SSE vs Polling

  • WebSocket vs Server-Sent Events (SSE): SSE lebih mudah didebug dan otomatis reconnect di atas HTTP/2, tapi sifatnya unidirectional. KDS membutuhkan interaksi 2 arah berfrekuensi tinggi (koki menekan tombol bump dan status ACK berulang-ulang), sehingga WebSocket jauh lebih efisien tanpa overhead HTTP header di setiap bump.
  • Redis Pub/Sub vs Redis Streams: Pub/Sub murni sangat cepat untuk broadcast instan, tapi tidak menyimpan riwayat jika tablet sedang offline. Solusi level senior mengombinasikannya dengan Redis Streams (XADD) untuk mengambil selisih delta saat tablet reconnect.
