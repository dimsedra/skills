Membedah Arsitektur WebSocket pada Kitchen Display System (KDS)

1. Mental Model & Intuisi Sistem

The Governing Invariant (Prinsip Dasar)

Kitchen Display System (KDS) bukan sekadar aplikasi chat biasa di mana pesan yang hilang bisa dimaklumi. KDS adalah state machine terdistribusi untuk operasional restoran. Jika satu frame WebSocket berisi pesanan steak hilang, atau sinyal "Batalkan Meja 4" datang terlambat/out-of-order, akibatnya fatal: makanan terbuang, koki salah masak, dan restoran merugi.

Prinsip mutlak dalam arsitektur WebSocket KDS level senior adalah: "Jangan pernah menganggap status koneksi socket mencerminkan status data bisnis." Koneksi WebSocket hanyalah pipa transfer data yang rapuh (*ephemeral*); tablet KDS harus bertindak sebagai *reconciliation engine* mandiri dengan pelacakan urutan monotonik, buffer offline, dan mekanisme *catch-up recovery*.

Analogi Dapur Nyata: Protokol "Line Expeditor"

Bayangkan koneksi WebSocket seperti suara Head Expeditor yang berteriak di dapur:

  • The Shout (Inbound Frame): Expeditor berteriak: "2 Ribeye Medium Rare Meja 12!"
  • The Read-Back (Application ACK): Koki panggangan langsung menjawab: "2 Ribeye Med Rare Meja 12 Siap!" Jika dalam 2 detik expeditor tidak mendengar jawaban balik, ia akan mengulang teriakannya.
  • The Kitchen Noise / Network Partition: Jika suara blender menenggelamkan teriakan expeditor, koki segera melihat papan tulis fisik (Snapshot Re-synchronization) agar tidak ada pesanan yang terlewat.

2. Fondasi Teori CS & Riset Terverifikasi

Membangun KDS yang tangguh memerlukan pemahaman mendalam tentang cara kerja RFC 6455 di atas lapisan transport TCP dan mengapa HTTP polling biasa tidak mencukupi.

Mekanisme Protokol: RFC 6455 Full-Duplex Layering

WebSocket diawali dengan handshake HTTP Upgrade (101 Switching Protocols). Setelah tersambung, koneksi TCP berganti ke mode frame biner/teks dengan overhead sangat kecil (frame header 2–14 byte, jauh lebih hemat dibanding HTTP header yang mencapai ~800 byte).

RFC 6455 menyediakan control frame bawaan: 0x9 (Ping) dan 0xA (Pong). Namun, API JavaScript di browser tidak mengekspos frame control ini ke developer. Oleh karena itu, frontend KDS wajib mengimplementasikan *Application-Level Heartbeat* manual untuk mendeteksi socket yang mati suri (*zombie socket*).

Masalah "Half-Open Socket" pada Wi-Fi Dapur yang Ekstrem

Di lingkungan dapur restoran, halangan fisik (dinding stainless steel, microwave, kulkas freezer besar) kerap menimbulkan *packet loss* mendadak. Saat tablet masuk ke area blind spot, socket di OS tetap berstatus ESTABLISHED karena timeout TCP keep-alive bawaan OS mobile bisa mencapai 2 jam.

Tanpa heartbeat berkala (misalnya interval 5 detik), server akan terus memompa pesanan ke socket yang sudah mati (*black hole*), mengakibatkan pesanan di layar koki tidak pernah muncul.

3. Topologi Arsitektur & Distributed Fanout

Dalam dapur multi-stasiun (Panggangan/Grill, Penggorengan/Fryer, Salad, Expo), pesanan dari POS atau platform online masuk melalui API Gateway, diteruskan ke message broker (Redis Pub/Sub), dan di-fanout secara spesifik ke layar stasiun yang bersangkutan.

src/kds/network/ResilientKDSClient.ts — Heartbeat Watchdog & Jittered Reconnection 
export class ResilientKDSClient {
  private ws: WebSocket | null = null;
  private url: string;
  private stationId: string;
  private lastMonotonicSeq = 0;
  private reconnectAttempts = 0;
  private heartbeatTimer?: number;
  private pongTimeoutTimer?: number;

  private readonly HEARTBEAT_INTERVAL_MS = 5000;
  private readonly PONG_TIMEOUT_MS = 3000;
  private readonly MAX_BACKOFF_MS = 15000;

  constructor(url: string, stationId: string) {
    this.url = url;
    this.stationId = stationId;
  }

  public connect(): void {
    this.cleanup();
    this.ws = new WebSocket(`${this.url}?station=${this.stationId}`);

    this.ws.onopen = () => {
      this.reconnectAttempts = 0;
      this.startHeartbeatWatchdog();
      this.reconcileMissedEvents();
    };

    this.ws.onmessage = (event) => {
      const payload = JSON.parse(event.data);
      if (payload.type === 'PONG') {
        clearTimeout(this.pongTimeoutTimer);
        return;
      }
      this.handleOrderEvent(payload);
    };

    this.ws.onclose = () => this.scheduleReconnection();
    this.ws.onerror = () => this.ws?.close();
  }

  private startHeartbeatWatchdog(): void {
    this.heartbeatTimer = window.setInterval(() => {
      if (this.ws?.readyState === WebSocket.OPEN) {
        this.ws.send(JSON.stringify({ type: 'PING', timestamp: Date.now() }));
        this.pongTimeoutTimer = window.setTimeout(() => {
          console.warn('[KDS] Heartbeat pong timeout! Socket mati suri. Memaksa close.');
          this.ws?.close();
        }, this.PONG_TIMEOUT_MS);
      }
    }, this.HEARTBEAT_INTERVAL_MS);
  }

  private scheduleReconnection(): void {
    this.cleanup();
    this.reconnectAttempts++;
    
    // Exponential Backoff dengan Full Jitter
    const baseBackoff = Math.min(this.MAX_BACKOFF_MS, 1000 * Math.pow(1.5, this.reconnectAttempts));
    const jitteredDelay = Math.random() * baseBackoff;

    window.setTimeout(() => this.connect(), jitteredDelay);
  }

  private handleOrderEvent(event: { seq: number; type: string; ticket: any }): void {
    // Verifikasi urutan monotonik: Deteksi duplikat atau paket yang hilang
    if (event.seq <= this.lastMonotonicSeq) {
      console.warn(`[KDS] Mengabaikan event duplikat atau usang: seq ${event.seq}`);
      return;
    }
    
    if (event.seq > this.lastMonotonicSeq + 1) {
      console.warn(`[KDS] Gap urutan terdeteksi (ekspektasi ${this.lastMonotonicSeq + 1}, terima ${event.seq}). Memicu resync snapshot.`);
      this.reconcileMissedEvents();
    }

    this.lastMonotonicSeq = event.seq;
    // Dispatch ke reactive store lokal (misal: Zustand)
    this.dispatchTicketToStore(event.ticket);
  }

  private async reconcileMissedEvents(): Promise {
    const res = await fetch(`/api/kds/snapshot?station=${this.stationId}&sinceSeq=${this.lastMonotonicSeq}`);
    const data = await res.json();
    this.hydrateLocalStore(data.activeTickets);
    this.lastMonotonicSeq = data.latestSeq;
  }

  private cleanup(): void {
    clearInterval(this.heartbeatTimer);
    clearTimeout(this.pongTimeoutTimer);
    if (this.ws) {
      this.ws.onopen = null;
      this.ws.onmessage = null;
      this.ws.onclose = null;
      this.ws.onerror = null;
      this.ws.close();
      this.ws = null;
    }
  }
}

① Inisialisasi & Konfigurasi Timer

Input: Target stasiun dapur (misal: GRILL) dan pelacakan urutan nomor urut terakhir (lastMonotonicSeq). Menyiapkan batas watchdog 5s dan batas backoff 15s.

② Watchdog Terminasi Zombie Socket

Mekanika: Mengirim PING setiap 5 detik. Jika dalam 3 detik tidak ada balasan PONG, panggil ws.close() secara paksa tanpa menunggu timeout TCP bawaan OS yang bisa memakan waktu 2 jam.

③ Exponential Backoff + Full Jitter

Anti-Thundering Herd: Menghitung delay dengan formula Math.random() * (1000 * 1.5^attempts). Menghindari tabrakan serentak puluhan tablet saat access point Wi-Fi dapur baru menyala kembali.

④ Deteksi Gap Urutan Monotonik

Verifikasi State: Membandingkan event.seq. Nomor duplikat/usang langsung diabaikan. Jika nomor urut melompat (terjadi packet loss), otomatis memicu pemulihan snapshot.

⑤ Snapshot Catch-up Recovery

Output: Mengambil active tickets terbaru dari REST API snapshot untuk menyinkronkan data yang terlewat selama jaringan terputus.

src/server/gateway/KDSWebSocketGateway.ts — Fanout Stasiun via Redis Pub/Sub 
import { WebSocketServer, WebSocket } from 'ws';
import { createClient } from 'redis';

export class KDSWebSocketGateway {
  private wss: WebSocketServer;
  private redisSub = createClient({ url: process.env.REDIS_URL });
  private stationClients = new Map<string, Set<WebSocket>>();

  constructor(port: number) {
    this.wss = new WebSocketServer({ port });
    this.init();
  }

  private async init(): Promise<void> {
    await this.redisSub.connect();

    // Subscribe ke pola channel multi-stasiun
    await this.redisSub.pSubscribe('kds:station:*', (message, channel) => {
      const stationId = channel.replace('kds:station:', '');
      this.broadcastToStation(stationId, message);
    });

    this.wss.on('connection', (ws: WebSocket, req) => {
      const url = new URL(req.url || '', 'http://localhost');
      const station = url.searchParams.get('station') || 'DEFAULT';

      if (!this.stationClients.has(station)) {
        this.stationClients.set(station, new Set());
      }
      this.stationClients.get(station)!.add(ws);

      ws.on('message', (raw) => {
        try {
          const msg = JSON.parse(raw.toString());
          if (msg.type === 'PING') {
            ws.send(JSON.stringify({ type: 'PONG', timestamp: Date.now() }));
          }
        } catch (err) {
          console.error('[Gateway] Format pesan tidak valid', err);
        }
      });

      ws.on('close', () => {
        this.stationClients.get(station)?.delete(ws);
      });
    });
  }

  private broadcastToStation(stationId: string, message: string): void {
    const clients = this.stationClients.get(stationId);
    if (!clients || clients.size === 0) return;

    for (const ws of clients) {
      if (ws.readyState === WebSocket.OPEN) {
        ws.send(message);
      }
    }
  }
}

① Setup Gateway & Client Registry

Membuat server WebSocket mandiri dan inisialisasi koneksi Redis subscriber serta Map registry untuk client per stasiun.

② Pattern-Based Redis Subscription

Ingress: Mendengarkan channel kds:station:* secara dinamis agar gateway dapat mendistribusikan event stasiun tanpa hardcode.

③ Routing Registry per Stasiun

Mengelompokkan koneksi tablet ke dalam Set<WebSocket> berdasarkan parameter ?station=GRILL.

④ Fast-Path Heartbeat Pong Echo

Merespons PING dari tablet seketika dengan pesan PONG tanpa membebani event loop backend.

⑤ Pencegahan Memory Leak

Menghapus referensi socket dari Set saat socket tertutup agar tidak terjadi akumulasi objek di V8 heap.

⑥ Targeted Station Fanout

Output: Memancarkan pesan hanya ke tablet yang terdaftar di stasiun tersebut, menghemat network bandwidth di tablet lain.

5. Trade-offs & Failure Modes Level Senior

Edge Cases & Hidden Failure Modes

  • The "Ghost Cook Bump" (Jebakan Optimistic UI): Koki menekan tombol "Selesai Dimasak" tepat saat sinyal Wi-Fi terputus. Jika UI langsung menghilangkan tiket tanpa antrean retry offline, pesanan hilang dari layar tablet tapi di server masih berstatus pending (driver pengantar menunggu selamanya). Solusi: Gunakan antrean offline IndexedDB dengan persistent replay.
  • Balapan Pembatalan Out-of-Order: Kasir membatalkan item 500ms setelah order dibuat. Jika latensi jaringan menunda event pembuatan, sinyal pembatalan bisa tiba lebih dulu. Solusi: Gunakan Monotonic Sequence ID / Lamport Timestamps. Jika pembatalan tiba untuk ID yang belum ada, buat tombstone record di state lokal.

Trade-offs Arsitektur: WebSocket vs SSE vs Long Polling

  • WebSocket vs Server-Sent Events (SSE): SSE lebih simpel dan berjalan di atas HTTP/2, tapi sifatnya unidirectional (hanya server ke client). Karena KDS butuh komunikasi 2 arah berfrekuensi tinggi (koki bump status, pause timer, kirim ACK), WebSocket jauh lebih hemat karena tanpa overhead HTTP header di setiap bump.
  • Redis Pub/Sub vs Redis Streams: Redis Pub/Sub sangat cepat dengan latensi sub-milidetik untuk broadcast, tapi tidak menyimpan riwayat. Kita kombinasikan dengan Redis Streams (XADD) atau database utama agar tablet yang baru reconnect bisa memutar ulang (*replay*) tiket yang tertinggal.
