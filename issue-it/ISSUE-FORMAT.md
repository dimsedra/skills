# Issue Format & Schema

Reference specifications, cognitive rationale, CLI publishing templates, and archetypes for issues generated by `/issue-it`.

---

## 1. Structural Rationale

Every section is engineered for the reader reviewing the issue six weeks later with zero active context:

- **Title (Problem-First)**: State the exact failure condition or system gap. Skimming the title in a tracker list must convey what is broken without opening the issue.
  - *Good:* `Auth token expiration bypasses database check during high-load requests`
  - *Avoid:* `Fix token check in auth.ts`
- **Big-Picture Context (Re-Orientation)**: 1–2 concise sentences framing where this component fits in the overall system architecture before detailing the defect.
- **Problem Description & Impact**: Clear explanation of what breaks, under what conditions it manifests, and the operational impact.
- **Affected Locations (Durable Symbol Pointers)**: Stable symbol names (functions, classes, methods, endpoints) and file paths (`path/to/file.ext` -> `SymbolName()`). Strictly no fenced code blocks or brittle line numbers; code snippets rot into stale snapshots.
- **Proposed Direction (Optional)**: High-level architectural strategy and boundaries. Do NOT include pseudo-code or implementation snippets.

---

## 2. Standard Issue Markdown Schema

```markdown
## Context
[1–2 sentences framing high-level system context for cold re-orientation]

## Problem Description
[Clear explanation of the specific failure condition, triggers, and operational impact]

## Affected Locations
- `path/to/file.ext` -> `SymbolName()`
- `path/to/another_file.ext` -> `ClassName.methodName()`

## Proposed Direction (Optional)
[High-level architectural approach or boundary adjustments]
```

---

## 3. GitHub CLI Publishing (`gh issue create`)

When the user confirms direct publishing to GitHub, construct and execute the `gh issue create` command:

```bash
gh issue create \
  --title "<Problem-First Title>" \
  --body "$(cat <<'EOF'
## Context
<High-level system context>

## Problem Description
<Failure description and impact>

## Affected Locations
- `path/to/file.ext` -> `SymbolName()`

## Proposed Direction
<High-level strategy>
EOF
)"
```

## 4. Concrete Archetype Examples

### Archetype A: Bug Report / Defect
```markdown
Title: Background job worker silently drops failed retries when dead-letter queue is unreachable

## Context
The task processing subsystem processes asynchronous background jobs using Celery workers with a secondary dead-letter queue fallback for unrecoverable errors.

## Problem Description
When the primary dead-letter queue broker experiences a network partition, the worker process catches the communication error but fails to log or persist the failed job payload, causing silent task drops without alerting monitoring systems.

## Affected Locations
- `src/workers/task_runner.py` -> `TaskRunner.handle_failure()`
- `src/workers/dlq_client.py` -> `DeadLetterQueueClient.publish_dead_letter()`

## Proposed Direction
Add local disk buffer fallback when the dead-letter queue is unreachable and emit a critical alert metric on failure.
```

### Archetype B: Architectural / State Gap
```markdown
Title: Optimistic UI state diverges on concurrent multi-tab mutations

## Context
The frontend workspace client manages optimistic document tree updates via a local Zustand store synchronized with backend WebSocket delta events.

## Problem Description
When two browser tabs submit conflicting tree node moves within the same debounce window, the local store reconciles incoming server state without re-basing local pending mutations, leaving the client UI state out of sync until a full page refresh.

## Affected Locations
- `src/features/workspace/store/treeSlice.ts` -> `applyTreeDelta()`
- `src/features/workspace/hooks/useWorkspaceSync.ts` -> `useWorkspaceSync()`

## Proposed Direction
Introduce a monotonic client-side version vector to optimistic mutations and reject stale deltas during reconciliation.
```

### Archetype C: Security / Auth Boundary
```markdown
Title: Tenant isolation missing on batch export endpoint allows cross-organization data retrieval

## Context
The analytics subsystem provides CSV/JSON reporting endpoints scoped to the requesting organization's tenant context.

## Problem Description
The batch export endpoint validates organization tenancy for single-report requests, but omits tenant ID filtering when processing multi-report batch arrays, enabling authenticated users to query report IDs belonging to other organizations.

## Affected Locations
- `src/api/controllers/export_controller.go` -> `ExportController.HandleBatchExport()`
- `src/services/reporting/exporter.go` -> `ReportExporter.FetchBatchRecords()`

## Proposed Direction
Enforce tenant ID validation in `ReportExporter.FetchBatchRecords()` by injecting the authenticated tenant context into the repository query builder.
```
